## 二、七系统关系总览

7 个系统不是并列的——它们分三层，调用关系完全不同：

```text
┌─ 技能层 ────────────────────────────────────────────────┐
│  宿主平台技能目录 · SKILL.md + scripts/ · 无独立进程      │
│                                                        │
│  skill-standardization（审计引擎，元层——审计其他技能）     │
│  semantic-split            activity-duration-estimation │
└────────────────────┬───────────────────────────────────┘
                     │ subprocess 真跑技能脚本
┌─ 编排器层 ──────────┴───────────────────────────────────┐
│  第 I 代  orchestrator (v2.8.1)                         │
│    人工编排 Pipeline → subprocess 跑技能脚本              │
│  第 II 代  silprespec-orchestrator (v0.1.0, 实验)        │
│    14 种穷举组合前置规范 → HTTP 调智能体 API              │
└────────────────────┬───────────────────────────────────┘
                     │ HTTP POST 调智能体 API
┌─ 智能体层 ──────────┴───────────────────────────────────┐
│  maby_agent 仓库 · 独立 HTTP 服务 · main.py 起进程        │
│  rag-assistant (8765/8767)   structured-writer (8770)   │
└────────────────────────────────────────────────────────┘
```

**关键区分——两代编排器调的对象不同**：

- **第 I 代 orchestrator 调技能**：subprocess 真跑 skill 脚本（可执行过滤，32 个技能入池），中间是死的、LLM 只做两头
- **第 II 代 silprespec-orchestrator 调智能体**：HTTP POST 调智能体 API（rag-assistant、structured-writer），LLM 填空生成工具输入，交付给智能体走内部流程——编排器不替智能体干活

技能与智能体是两类完全不同的存在：**技能**是跨平台分发的扩展单元（SKILL.md 声明 + scripts 脚本，无独立进程，由任意宿主平台加载，也可被编排器以 subprocess 调用）；**智能体**是独立 HTTP 服务（自带 Web UI 与外部 API，自己起进程自己管端口，被编排器以 API 调用）。运行方式见附录 B 运行速查。

## 三、实验性说明

架构 06、07 标注**实验性**：系统代码已实现（orchestrator v2.8.1、silprespec-orchestrator v0.1.0——14 种穷举组合、六类输入分类、ProgressMap 进度地图等机制均已落地），但**端到端的实验验证仍在进行中**，架构可能随实验结果调整。它们代表方法论当前正在探索的方向——**从"单系统内的前置规范"走向"多系统编排层的前置规范"**。实验收敛后，这两篇会随工具迭代更新并去掉实验性标注；母书如出后续版本，亦将收录其沉淀出的方法论结论。
